\section{Wstęp}

Każdy przedmiot na studiach ma swój sylabus. To w nim prowadzący zapisuje, czego student ma się nauczyć, ile jest godzin wykładów i laboratoriów, za ile przedmiot jest punktów ECTS, jak wygląda zaliczenie i z jakich książek warto korzystać. Uczelnia musi te informacje udostępniać, co wynika z ustawy Prawo o szkolnictwie wyższym i nauce \cite{ustawa_psw}. Zasady liczenia punktów ECTS opisuje z kolei europejski system ECTS \cite{ects_guide}.

Mimo to sylabusy bardzo często powstają w Wordzie i krążą mailem między prowadzącym a dziekanatem. Szybko robi się z tego kilka wersji tego samego pliku i nie wiadomo, która jest aktualna. Nie widać też, kto i kiedy coś w nim zmienił. Jeszcze trudniej jest na uczelni, która ma kilka ośrodków w różnych miastach. Ten sam przedmiot ma wtedy kilka sylabusów, które z roku na rok coraz bardziej się od siebie różnią. Sprawdzenie, czy liczba godzin pasuje do punktów ECTS, zwykle oznacza liczenie na kartce.

W ramach projektu napisałem aplikację \textbf{SyllabusApp}, czyli webowy system do zarządzania sylabusami. Sylabusy wprowadza się w niej przez formularze. Każda zmiana zapisuje się jako nowa wersja, więc historia dokumentu jest zawsze dostępna. Aplikacja pozwala też wyszukiwać i filtrować sylabusy, pokazuje siatkę przedmiotów dla kierunku, pilnuje poprawności liczby godzin i eksportuje sylabus do PDF albo DOCX.

Całość napisałem na platformie .NET 10. Backend to ASP.NET Core Web API \cite{ms_aspnetcore}, frontend powstał w Blazor WebAssembly \cite{ms_blazor}, a dane trzyma baza PostgreSQL \cite{postgresql}, z którą aplikacja łączy się przez Entity Framework Core \cite{ms_efcore}. Wszystko uruchamia się w kontenerach Docker \cite{docker}. Projekt ma też testy jednostkowe i prosty monitoring stanu aplikacji.

\section{Cel projektu}

\subsection{Problem}

Najważniejszy problem to brak jednego miejsca, w którym są aktualne sylabusy. Kiedy dokumenty leżą w różnych plikach i skrzynkach mailowych, każdy na tym traci. Prowadzący co roku poprawia te same treści od nowa. Dziekanat musi ręcznie sprawdzać, czy sylabusy zgadzają się z programem studiów. Student nie ma pewności, czy czyta aktualną wersję.

\subsection{Cele}

Chciałem zbudować aplikację webową, która:
\begin{itemize}
  \item trzyma sylabusy w bazie danych i wiąże je z ośrodkiem, wydziałem, kierunkiem, przedmiotem i rokiem akademickim,
  \item ma formularze na wszystkie elementy sylabusa,
  \item przy każdej zmianie sama zapisuje nową wersję, żeby dało się odtworzyć historię,
  \item sprawdza poprawność danych, przede wszystkim to, czy godziny zgadzają się z ECTS,
  \item pozwala szybko znaleźć sylabus po kilku kryteriach,
  \item pokazuje siatkę przedmiotów kierunku z podziałem na semestry,
  \item eksportuje sylabus do PDF i DOCX,
  \item wpuszcza tylko zalogowanych użytkowników i rozróżnia ich role.
\end{itemize}

\subsection{Wymagania niefunkcjonalne}

Poza samymi funkcjami zależało mi na kilku ogólniejszych rzeczach. Do API można się dostać tylko z ważnym tokenem JWT, a uprawnienia zależą od roli (administrator, dziekan, wykładowca, student). Hasła nie są nigdzie zapisane wprost. Cały system (baza, API i frontend) startuje jednym poleceniem \texttt{docker compose up}, więc nie trzeba niczego instalować ręcznie.

Kod podzieliłem na warstwy według zasad czystej architektury \cite{martin_clean}. Każda encja jest obsługiwana według tego samego schematu: DTO, serwis, kontroler, klient API i strony. Dzięki temu łatwo się w nim odnaleźć. Stan aplikacji można sprawdzić pod adresem \texttt{/health}, a logikę biznesową sprawdzają testy uruchamiane przez \texttt{dotnet test}. Interfejs jest po polsku, a komunikaty o błędach mówią wprost, co trzeba poprawić.

\section{Przegląd istniejących rozwiązań}

W Polsce sylabusy obsługuje kilka systemów. Zwykle są to moduły dużych systemów do zarządzania całą uczelnią.

\subsection{USOS}

USOS, czyli Uniwersytecki System Obsługi Studiów \cite{usos}, rozwija Międzyuniwersyteckie Centrum Informatyzacji. Korzysta z niego kilkadziesiąt polskich uczelni. Opisy przedmiotów leżą w katalogu przedmiotów i są publikowane w serwisie USOSweb. System obsługuje cykle dydaktyczne, efekty uczenia się powiązane z Polską Ramą Kwalifikacji i rozbudowane programy studiów. Ma też publiczne API \cite{usos_api} z autoryzacją OAuth, przez które mogą się z nim łączyć inne aplikacje.

Zaletą USOS-a jest ogromny zakres funkcji i połączenie z rekrutacją, ocenami i planem zajęć. Wadą jest to, że wdrożenie i utrzymanie są skomplikowane, a edycja sylabusów nie należy do wygodnych. System jest też przeznaczony głównie dla uczelni publicznych z konsorcjum.

\subsection{Akademus}

Akademus \cite{akademus} to komercyjny system do zarządzania uczelnią. Ma między innymi moduł programów studiów i sylabusów. Można w nim tworzyć karty przedmiotów, przypisywać efekty uczenia się, generować dokumenty i publikować je na stronie uczelni.

Plusem są gotowe szablony dokumentów i moduł sprawozdawczy. Minusem jest to, że system jest zamknięty i płatny, a sylabusy to tylko jego mały fragment, więc nie da się łatwo wdrożyć samego tego modułu.

\subsection{Uczelnia.XP}

Uczelnia.XP \cite{uczelniaxp} firmy Asseco Data Systems to system obsługi toku studiów. W module planów i programów studiów przygotowuje się w nim sylabusy zgodne z PRK. Jest też obieg zatwierdzania dokumentów.

System dobrze współpracuje z dziekanatem i ma wsparcie producenta. Z drugiej strony licencja jest droga, interfejs dość ciężki, a uczelnia uzależnia się od jednego dostawcy.

Wartości enumeracji przesyłam jako tekst (np. \texttt{"Draft"}), bo łatwiej się wtedy czyta odpowiedzi API. \section{Opis implementacji}

\subsection{Frontend}

Frontend to aplikacja jednostronicowa (SPA) napisana w Blazor WebAssembly \cite{ms_blazor}. Wybrałem Blazora, bo pozwala pisać interfejs w C\#, tym samym języku co backend, i korzystać z tych samych klas DTO. Wygląd oparłem na Tailwind CSS \cite{tailwind}. Zdefiniowałem kilka własnych klas (\texttt{btn-primary}, \texttt{form-input}, \texttt{data-table}), żeby wszystkie strony wyglądały tak samo.

Kod frontendu jest podzielony na kilka folderów:
\begin{itemize}
  \item \texttt{Pages/} zawiera strony aplikacji, czyli logowanie i rejestrację, listy i formularze dla ośrodków, wydziałów, kierunków, przedmiotów, grup i sylabusów oraz siatkę przedmiotów,
  \item w \texttt{Services/ApiClients/} są klienci REST API, po jednym na każdy zasób,
  \item w \texttt{Auth/} jest \texttt{TokenAuthenticationStateProvider}, który odczytuje dane i role użytkownika, oraz \texttt{AuthorizationMessageHandler}, który dokleja token do zapytań,
  \item \texttt{Layout/} to układ strony z menu po lewej i informacją o zalogowanym użytkowniku.
\end{itemize}

To, co widzi użytkownik, zależy od jego roli. Przyciski dodawania, edycji i usuwania pokazują się tylko administratorom i wykładowcom (komponent \texttt{AuthorizeView}). Strony, które wymagają logowania, mają atrybut \texttt{[Authorize]}. Ekran logowania widać na rysunku \ref{fig:logowanie}.

\subsection{Backend}

Backend to aplikacja ASP.NET Core Web API \cite{ms_aspnetcore}. Wszystkie zasoby obsługuję według jednego schematu. Kontroler przyjmuje i zwraca DTO, a samą pracę zleca serwisowi. Interfejs serwisu leży w \texttt{Application}, a implementacja w \texttt{Infrastructure} i to ona korzysta z \texttt{SyllabusDbContext}. Serwisy są rejestrowane w kontenerze zależności jako \textit{scoped}. Kiedy operacja może się nie udać z powodów biznesowych (np. nie ma takiego przedmiotu), serwis nie rzuca wyjątku, tylko zwraca obiekt wyniku, np. \texttt{SyllabusResult}. Kontroler zamienia go na właściwy kod HTTP: 200, 201, 400 albo 404.

\subsubsection{Uwierzytelnianie i autoryzacja}

Użytkowników i role obsługuje ASP.NET Core Identity \cite{ms_identity}. Hasło musi mieć co najmniej 8 znaków, w tym cyfrę, małą i wielką literę. Po pięciu nieudanych próbach konto blokuje się na 15 minut. Gdy logowanie się powiedzie, \texttt{TokenService} tworzy token JWT podpisany algorytmem HMAC-SHA256. W tokenie są identyfikator, e-mail, imię, nazwisko i role użytkownika. Nowe konto dostaje rolę \textit{Student}. Role i konto administratora tworzy przy starcie aplikacji klasa \texttt{DataSeeder}. Żeby zmieniać dane, trzeba mieć rolę \textit{Admin} albo \textit{Lecturer}, co pilnuje atrybut \texttt{[Authorize(Roles = \ldots)]}.

\subsubsection{Research: logowanie kontem uczelnianym}
\label{sec:research}

Przy wymaganiu logowania kontem uczelnianym trzeba było najpierw sprawdzić, jakie są możliwości. Wziąłem pod uwagę dwie.

Pierwsza to OpenID Connect z Microsoft Entra ID \cite{oidc,ms_entra}. Większość polskich uczelni, w tym SAN, daje studentom i pracownikom konta Microsoft 365 w swojej domenie. Aplikację rejestruje się w Entra ID, a logowanie przebiega według schematu \textit{Authorization Code} z PKCE. We frontendzie można użyć biblioteki MSAL dla Blazor WebAssembly, a backend sprawdza token wydany przez Entra ID (\texttt{AddMicrosoftIdentityWebApi}). Żeby wpuszczać tylko osoby z jednej uczelni, ustawia się identyfikator dzierżawy (\textit{tenant ID}).

Druga możliwość to USOS API \cite{usos_api}. Uczelnie, które korzystają z USOS-a, udostępniają API z autoryzacją OAuth 1.0a. Można przez nie potwierdzić tożsamość studenta i pobrać np. jego numer albumu i kierunek. Trzeba jednak dostać klucz aplikacji od administratora USOS-a na danej uczelni.

Lepszym wyborem jest moim zdaniem Entra ID. Opiera się na otwartych standardach \cite{rfc6749,oidc}, .NET dobrze go obsługuje i działa także na uczelniach bez USOS-a. W obecnej architekturze wystarczyłoby dodać w API drugi sposób uwierzytelniania i endpoint, który po sprawdzeniu tokenu z Entra ID znajdzie (albo utworzy) użytkownika po adresie e-mail i wyda mu zwykły token JWT aplikacji. Role, autoryzacja i frontend zostałyby bez zmian. Tej integracji nie uruchomiłem, bo rejestracja aplikacji w dzierżawie uczelni wymaga uprawnień administratora IT.

\subsubsection{Wersjonowanie i historia zmian}

Za każdym razem, gdy sylabus jest zapisywany, powstaje nowy rekord \texttt{SyllabusVersion}. Przy tworzeniu sylabusa jest to wersja 1 z opisem ,,Utworzenie sylabusa'', a każda kolejna edycja dodaje wersję z numerem o jeden większym. W wersji zapisuję najważniejsze pola (rok, ECTS, godziny, cele, ocenianie, wymagania), autora, datę, opis zmian i pełną kopię sylabusa w JSON (listing \ref{lst:wersje}). Unikalny indeks na parze (\texttt{SyllabusId}, \texttt{VersionNumber}) nie pozwala, żeby dwie wersje miały ten sam numer.

\begin{lstlisting}[language={[Sharp]C}, caption={Zapis nowej wersji przy edycji sylabusa (fragment \texttt{SyllabusService})}, label={lst:wersje}]
syllabus.ApplyUpdate(dto);
syllabus.UpdatedAt = DateTime.UtcNow;
await _dbContext.SaveChangesAsync();

var lastVersion = await _dbContext.SyllabusVersions
    .Where(v => v.SyllabusId == id)
    .MaxAsync(v => (int?)v.VersionNumber) ?? 0;
var description = string.IsNullOrWhiteSpace(dto.ChangeDescription)
    ? "Aktualizacja sylabusa" : dto.ChangeDescription.Trim();
await AddVersionAsync(syllabus, lastVersion + 1, description, userId);
\end{lstlisting}

\subsubsection{Walidacja danych}

Dane są sprawdzane na dwa sposoby. Atrybuty \texttt{DataAnnotations} pilnują pól wymaganych, długości tekstu i formatu roku akademickiego (\texttt{RRRR/RRRR}). Reguły dotyczące godzin wydzieliłem do klasy \texttt{SyllabusRules} (listing \ref{lst:reguly}). Zgodnie z zasadami ECTS \cite{ects_guide} przyjąłem, że jeden punkt to 25--30 godzin pracy studenta. Z tego wynikają następujące reguły:
\begin{itemize}
  \item ECTS musi być w zakresie od 1 do 30,
  \item godziny nie mogą być ujemne, a sylabus musi mieć przynajmniej jedną godzinę zajęć,
  \item wszystkie godziny zajęć razem nie mogą przekroczyć ECTS $\times$ 30,
  \item suma nakładu pracy studenta powinna wynosić od ECTS $\times$ 25 do ECTS $\times$ 30 godzin, a jeśli tak nie jest, na stronie sylabusa pojawia się ostrzeżenie.
\end{itemize}

\begin{lstlisting}[language={[Sharp]C}, caption={Reguły walidacji godzin (fragment \texttt{SyllabusRules})}, label={lst:reguly}]
public static List<string> ValidateHours(int ects, int lectureHours,
    int exerciseHours, int laboratoryHours)
{
    var errors = new List<string>();
    if (ects < MinEcts || ects > MaxEcts)
        errors.Add($"Liczba punktów ECTS musi mieścić się w zakresie {MinEcts}-{MaxEcts}.");
    if (lectureHours < 0 || exerciseHours < 0 || laboratoryHours < 0)
        errors.Add("Liczba godzin nie może być ujemna.");
    var contactHours = lectureHours + exerciseHours + laboratoryHours;
    if (contactHours <= 0)
        errors.Add("Sylabus musi mieć co najmniej jedną godzinę zajęć.");
    if (ects >= MinEcts && contactHours > ects * MaxHoursPerEcts)
        errors.Add($"Godziny zajęć ({contactHours} h) przekraczają ...");
    return errors;
}
\end{lstlisting}

Te reguły wywołuje klasa bazowa formularza \texttt{SyllabusEditDto}, która implementuje \texttt{IValidatableObject}. Projekt \texttt{Application} jest wspólny, więc ta sama walidacja działa w Blazorze, gdzie komunikat pojawia się pod polem, i w API, które zwraca wtedy kod 400.

\subsubsection{Wyszukiwanie i siatka przedmiotów}

Metoda \texttt{GetAllAsync(SyllabusFilterDto)} buduje zapytanie LINQ krok po kroku. Każde wypełnione pole filtra dokłada kolejny warunek \texttt{Where}. EF Core zamienia to na jedno zapytanie SQL ze złączeniami od sylabusa przez przedmiot, kierunek i wydział aż do ośrodka. Przy wyszukiwaniu tekstu wielkość liter nie ma znaczenia.

\texttt{GetCurriculumGridAsync} pobiera wszystkie przedmioty kierunku razem z ich sylabusami i grupuje je po semestrach. Dla każdego przedmiotu bierze sylabus z wybranego roku akademickiego, a jeśli rok nie jest podany, to najnowszy. Sumy godzin i ECTS liczą się same we właściwościach DTO.

\subsubsection{Eksport do PDF i DOCX}

Eksportem zajmuje się \texttt{SyllabusExportService}. Najpierw pobiera sylabus ze wszystkim, co z nim związane: przedmiotem, kierunkiem, wydziałem, ośrodkiem, prowadzącym, efektami, literaturą i nakładem pracy. Potem przygotowuje treść, która jest taka sama dla obu formatów: tabelę z danymi podstawowymi, sekcje z opisami i tabele efektów, literatury i nakładu pracy. PDF tworzy biblioteka QuestPDF \cite{questpdf} na licencji Community, w której układ strony opisuje się w kodzie C\#. DOCX tworzy Open XML SDK \cite{openxml}, więc na serwerze nie trzeba mieć zainstalowanego Office'a. Polskie znaki wyświetlają się poprawnie w obu formatach.

Aplikacja łączy się z nim przez Entity Framework Core 10 \cite{ms_efcore} i sterownik Npgsql \cite{npgsql}. Pracowałem w podejściu \textit{code first}: schemat bazy wynika z klas encji i konfiguracji w \texttt{SyllabusDbContext}, a każda zmiana schematu to nowa migracja. API przy starcie samo stosuje brakujące migracje (\texttt{Database.MigrateAsync()}), więc na nowej instalacji nie trzeba ręcznie zakładać tabel.

\subsection{Docker}

Każda część systemu ma własny obraz. Obraz API budowany jest w dwóch etapach. Najpierw \texttt{dotnet/sdk:10.0} kompiluje i publikuje aplikację, a potem gotowe pliki trafiają do dużo mniejszego obrazu \texttt{dotnet/aspnet:10.0}. Przy budowaniu frontendu najpierw powstaje arkusz Tailwind CSS, potem publikowana jest aplikacja Blazor, a gotowe pliki serwuje \texttt{nginx:alpine}. W konfiguracji nginx jest reguła \texttt{try\_files}, która każdy nieznany adres kieruje do \texttt{index.html}. Bez niej odświeżenie np. strony \texttt{/syllabuses} kończyłoby się błędem 404. Baza korzysta z oficjalnego obrazu \texttt{postgres:16-alpine}, a dane zapisuje w wolumenie.

Wszystkie kontenery opisuje plik \texttt{docker-compose.yml} (listing \ref{lst:compose}). Ustawienia API, czyli połączenie z bazą, klucz JWT, konto administratora i dozwolone adresy CORS, przekazuję przez zmienne środowiskowe. ASP.NET Core traktuje je jako ważniejsze od wartości z \texttt{appsettings.json}. API rusza dopiero wtedy, gdy baza zgłosi, że jest gotowa (\texttt{condition: service\_healthy}).

\begin{lstlisting}[caption={Fragment pliku \texttt{docker-compose.yml}}, label={lst:compose}]
  api:
    build:
      context: .
      dockerfile: src/SyllabusApp.Api/Dockerfile
    depends_on:
      db:
        condition: service_healthy
    environment:
      ConnectionStrings__DefaultConnection: "Host=db;Port=5432;..."
      Jwt__Key: "..."
      Cors__Origins__0: "http://localhost:8080"
    ports:
      - "8081:8080"
    healthcheck:
      test: ["CMD-SHELL", "curl -fs http://localhost:8080/health || exit 1"]
      interval: 15s
\end{lstlisting}

Żeby uruchomić cały system, wystarczy wpisać \texttt{docker compose up -d --build}. Frontend działa wtedy pod adresem \texttt{localhost:8080}, a API pod \texttt{localhost:8081}.

\subsection{Monitoring}

Do monitorowania użyłem mechanizmu \textit{health checks}, który jest wbudowany w ASP.NET Core \cite{ms_healthchecks}. W API dodałem sprawdzenie \texttt{AddDbContextCheck} dla \texttt{SyllabusDbContext}. Przy każdym wejściu na \texttt{/health} aplikacja próbuje połączyć się z bazą i odpowiada \texttt{Healthy} (kod 200) albo \texttt{Unhealthy} (kod 503).

\begin{lstlisting}[language={[Sharp]C}, caption={Konfiguracja health checks w \texttt{Program.cs}}, label={lst:health}]
builder.Services.AddHealthChecks()
    .AddDbContextCheck<SyllabusDbContext>("database");
app.MapHealthChecks("/health");
\end{lstlisting}

Z tego adresu korzysta Docker. Co 15 sekund sprawdza \texttt{/health} kontenera \texttt{api}, a bazę sprawdza poleceniem \texttt{pg\_isready}. Stan wszystkich usług (\texttt{healthy} albo \texttt{unhealthy}) pokazuje polecenie \texttt{docker compose ps}. Jeśli któryś kontener padnie, Docker sam go uruchomi ponownie (\texttt{restart: unless-stopped}). Do tego aplikacja zapisuje logi, m.in. zapytania SQL, błędy i zakładanie kont. Można je podejrzeć przez \texttt{docker compose logs api}.

\section{Podsumowanie i wnioski}

Aplikacja działa i spełnia wymagania projektu poza logowaniem kontem uczelnianym. Tego nie wdrożyłem, ale opisałem w researchu, jak można je dodać przez Microsoft Entra ID.

\subsection{Napotkane wyzwania}

Pierwszym problemem było to, żeby nie pisać tych samych reguł walidacji dwa razy. Rozwiązałem go wspólną klasą bazową formularza z \texttt{IValidatableObject}, która leży w projekcie używanym przez API i przez Blazora.

Drugi problem dotyczył enumeracji. .NET domyślnie wysyła je w JSON jako liczby, więc musiałem tak samo skonfigurować \texttt{JsonStringEnumConverter} po stronie API i frontendu. Inaczej deserializacja się wysypywała.

Kłopot sprawiło też pobieranie plików. Zwykły link nie wysyła tokenu JWT, więc API odrzucało takie zapytanie. Plik pobiera więc \texttt{HttpClient}, a zapisuje go na dysku krótka funkcja w JavaScripcie.

Przy budowaniu obrazu frontendu okazało się, że brakuje arkusza Tailwind CSS, bo nie jest on trzymany w repozytorium. Generuję go teraz w trakcie budowania obrazu, a adres API wpisuję do \texttt{appsettings.json} jako argument budowania. Ostatnia rzecz to pierwsze uruchomienie na pustej bazie w kontenerze. Żeby nie zakładać tabel ręcznie, API samo stosuje migracje przy starcie.

\subsection{Możliwości dalszego rozwoju}

\begin{itemize}
  \item wdrożyć logowanie kontem uczelnianym przez Microsoft Entra ID, tak jak opisałem w researchu,
  \item dodać obieg akceptacji sylabusa (wykładowca, potem dziekan), do którego jest już przygotowana encja \texttt{SyllabusApproval} i statusy,
  \item umożliwić porównanie dwóch wersji sylabusa i przywrócenie starszej,
  \item zrobić publiczny katalog opublikowanych sylabusów, dostępny bez logowania,
  \item rozbudować monitoring o metryki (Prometheus, Grafana) i zbieranie logów w jednym miejscu,
  \item dopisać testy integracyjne API i testy interfejsu,
  \item powiązać efekty uczenia się przedmiotu z efektami kierunkowymi i Polską Ramą Kwalifikacji.
\end{itemize}
